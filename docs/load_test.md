## How the service got here (earlier runs, different runners)

One run after each change: onnxruntime's pool sized to the host's cores, then to the container's quota, then one inference at a time, then one single-thread inference per CPU. **Each run landed on a different runner CPU**, and the int8 model's own time (third column) moves with the hardware, so these rows mix the service change with the machine; only the same-runner table above compares setups fairly. Files: `results/load_test_unpinned.json`, `results/load_test_pinned.json`, `results/load_test_serial.json`, `results/load_test_parallel.json`.

| CPUs | service | model ms, 1 client | 1 client p50 / p95 ms | 8 clients p50 / p95 ms | sustained req/s | usd per 1M |
|---:|---|---:|---:|---:|---:|---:|
| 1 CPU | threads = host cores — AMD EPYC 9V74 80-Core | 6.19 | 2.5 / 78.8 | 87.3 / 99.5 | 131 | $0.022 |
| 1 CPU | threads = CPU quota — AMD EPYC 7763 64-Core | 2.95 | 3.7 / 6.7 | 19.5 / 89.9 | 243 | $0.012 |

| 2 CPUs | threads = host cores — AMD EPYC 9V74 80-Core | 4.91 | 4.4 / 52.9 | 29.9 / 81.3 | 217 | $0.027 |

One change survives the hardware caveat: sizing the pool to the quota removed a tail at one client (p95 79 → 7 ms at 1 CPU, 53 → 5 ms at 2 CPUs). With one client nothing queues, so a tail of tens of ms on a model that takes a few is CPU-quota throttling, not a slower machine.

**Caveats.** A GitHub runner is not a t3.small: different CPU, and a t3 is burstable — run flat out it needs "unlimited" CPU credits, which cost extra. The load generator shares the runner with the server (outside its CPU limit, but on the same host). Runners differ in CPU generation from run to run, so absolute numbers move between runs; compare setups only within one run.
