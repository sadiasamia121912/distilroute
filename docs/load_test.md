## What each fix changed

The same load test after each change to the service: onnxruntime's thread pool sized to the host's cores (the first run), then to the container's CPU quota (`students.cpu_limit`), then inference serialised per model (`serve.py`, `DISTILROUTE_CONCURRENCY`), then — as an alternative to that — one single-thread inference per CPU (`DISTILROUTE_CONCURRENCY=<CPUs>`, `DISTILROUTE_THREADS=1`). Earlier runs: `results/load_test_unpinned.json`, `results/load_test_pinned.json`, `results/load_test_serial.json`.

| CPUs | service | 1 client p50 / p95 ms | 8 clients p50 / p95 ms | sustained req/s | usd per 1M |
|---:|---|---:|---:|---:|---:|
| 1 | threads = host cores | 2.5 / 78.8 | 87.3 / 99.5 | 131 | $0.022 |

| 2 | threads = CPU quota | 3.2 / 5.2 | 19.8 / 63.4 | 290 | $0.020 |
| 2 | + one inference at a time | 3.5 / 5.6 | 28.3 / 46.0 | 261 | $0.022 |
| 2 | + one single-thread inference per CPU | 1.8 / 2.7 | 8.2 / 18.1 | 878 | $0.007 |

With one client nothing is ever queued, so the pinned and serialised services run the same code there; their 1-client throughput still differs by up to 11%. That is the run-to-run noise of a shared runner, and smaller gaps are within it. Serialising shows under load: the model's own time stays flat as clients are added, and p95 falls while p50 rises, because requests now wait their turn. On 1 CPU the serial and parallel setups *should* be identical (one slot, and one thread if the quota is detected), yet they are 65% apart at one client, far beyond the 11% noise. So they were not the same: most likely the serial service did not detect the 1-CPU quota inside the container and still ran onnxruntime with several threads, and the gain credited to pinning came from its other settings. Unverified.

**Tail latency.** At 1 CPU and one client, the median request takes 1.5 ms but p95 is 2 ms. At 2 CPUs and one client, the median request takes 1.8 ms but p95 is 3 ms. The table above shows what each fix to the service changed.

**Caveats.** A GitHub runner is not a t3.small: different CPU, and a t3 is burstable — run flat out it needs "unlimited" CPU credits, which cost extra. The load generator shares the runner with the server (outside its CPU limit, but on the same host). One run per configuration; runner speed varies from day to day.
